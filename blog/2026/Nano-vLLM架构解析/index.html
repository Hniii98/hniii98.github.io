Nano-vLLM 架构解析 part1-engine

1. 数据流

Nano-vLLM 主要由 LLMEngine、ModelRunner、Scheduler三个核心部件构成。

Nano-vLLM 将用户的输入用 Sequence 封装并交给调度器进行调度，调度的结果由 Sequence 中的状态变量持有并且以 Sequence 实例的形式存在。LLMEngine将调度结果交给 ModelRunner进行推理，ModelRunner 管理推理实际需要状态和变量，将调度结果交给实际的模型进行前向推理，本例实际是 QWen3 。ModelRunner 接收到模型输出的 hidden state 先经过 LM head得到logits，再送进采样器到最终的 token id 交还给 LLMEngine。

2. 模块

2.1 Sequence

用户输入的 prompt 有时候需要多轮的推理才能够完成，因此需要有一个包装来持有这个原始的状态，同时prompt 在推理时需要的 kv block 映射、调度的切片结果等都需要保存、传递，Nano-vLLM用Sequcence管理。

  • 调度 ： Sequence中持有num_tokens、num_cached_token、num_scheduled_tokens三个变量分别表示序列中总的token数量、缓存的token数量、以及被调度的token数量。num_tokens随着序列增长在 postprocess() 中更新。num_cached_token 初始化时，在BlockManager中以 block_size 为粒度查询可复用的缓存块并记录大小，之后每个步在 postprocess() 中根据被调度的token数量更新对应的长度。被调度的token数由 num_scheduled_tokens 保存，当进行prefill 阶段的时候，调度器可能无法一次性对整个序列进行调度，因此需要记录被调度的长度供模型前向的时候进行切片。Nano-vLLM 只支持对 waitting 序列中的首序列进行 chunk prefill。

  • 传输： Nano-vllm 支持了单机多卡，不同 rank 之前的任务传输是通过 shared memory 的写入和读取实现的，主进程把需要执行的 method 和对应的 args 写入 shared memory。 Sequence中__getstate__() 和 __setstate__() 方法支持 pickle 对Sequence的自动序列化和反序列化。prefill时候完整传输tokens_id, decode则仅仅需要last_token。

2.2 BlockManager

PagedAttention 将 kv cache 切分成Block进行管理和复用，BlockManager实现对于Block生命周期的管理。

BlcokManager使用block_id去管理每个 kv block的使用情况。Nano-vLLM当前支持单机多卡，对于Attention的计算并行，每个 rank **负责各自 **head 切片的 o计算，在Attention 的子层后通过 dist.all_reduce 对各 rank 的计算结果进行求和，以此来保证下一层 layer 输入的正确性。每个 rank 上应用相同的block_table维护 token->slot的映射，只是不同的 rank 中 slot 存储的不同 head 对应 的 kv 值。

Block

kv block 通过block_id唯一标识, ref_count标识Block被复用的次数，token_ids持有当前Block内的token id, hash则记录完整前缀对应的哈希值，随着序列的增长不断更新。

Block 的使用和释放

BlockManager用 free_block_ids 和 used_block_ids管理使用和释放的Block。

kv block 必须前缀的哈希相等并且块内持有的 token_ids 相同才可以复用当前的 Block ，但是可能存在哈希碰撞的现象导致上述的条件成立但是完整序列不是一致的现象。vLLM采用的是更强的256位哈希来降低这种情况出现的概率。

当序列首次进入调度器后，调度器会通过 BlockManager 对序列进行逐块的前缀匹配直至匹配失败，并记录连续缓存命中的块数。这里缓存命中的Block可以在使用中，也可以被释放，因为Block释放后不会清楚其中存储的数据，以此来提高缓存的复用率。如果Block正在使用中，只需要简单的增加对应的ref_count来代表占用。如果Block释放了，就将对应的block_id移除释放队列，并修改ref_count。

对于没有匹配到前缀的剩余块，从释放的列表中申请对应数量的Block并且移除hash_to_block_id中的旧映射避免错误的复用，新的 kv 需要在前向完成后在 postprocess()中登记。

Block的释放逻辑非常简单，从free_block_ids移除，添加到used_block_ids中。postprocess()会检查序列是不是达到了eos标记或者超过了最长序列，满足条件的话就停止序列的继续生产，然后将涉及到的所有 Block 的 ref_count减1，如果发现此时 ref_count 为0了，就移入 free_block_ids。

Block的 hash 更新

当 Block 从free_block_ids移出的时候，hash被重置为-1，随着推理进行到 token 填充满整个 block_size 大小之后，** hash_blocks() ** 会更新 Block中持有的 hash 状态并且添加到 hash_to_block_id供其他的序列进行复用。

2.3 Scheduler

调度器通过 waiting 和 running 队列调度序列的 prefill 及 decode。

调度

Schduler 在schedule中实现了具体调度策略，总体上:

  • prefill 优先，decode次之。
  • 首个被调度的prefill序列允许 chunk prefill, 其他prefill要么完整调度剩余token，要么放弃调度。
  • 没有任何prefill序列被调度后，考虑调度decode序列 当序列被首次prefill时候，调度器会调用BlockManager中的方法检查连续命中的kv块数，并更新对应的block_table和Block的状态。

驱逐

当前只在 decode 中实现驱逐，驱逐的策略比较简单：驱逐running队列中的最新加入的序列，如果running序列为空，则驱逐当前序列。 驱逐序列需要将序列的状态重新标记为is_prefill。序列中缓存块Block的持有策略是None or all, 驱逐的时候需要全部释放所有缓存的Block。将对应的 ref_count减1，若ref_count变化到了0，更新 Block 的状态。同时，重置序列中中的block_table和num_cached_tokens, 将序列放回waiting等待重新重新调度进行 prefill。

后处理

LLMEngine在一个 step 之后会调用 postprocess()：

  • 更新本轮推理后涉及到的完整Block的哈希
  • 更新缓存的token数和调度的token数
  • 更新生成完成序列的状态

2.4 ModelRunner

ModelRunner负责持有实际进行前向推理的模型以及模型推理需要的状态和变量，当实现多卡时还需要负责指令及参数传递。

单机多卡

当初始化self.world_size > 1指示为单机多卡环境时。LLMEngine为子进程创建了ModelRunner作为执行入口，同时传递一个Event作为消息传递的变量。主进程的ModelRunner负责创建一个用于数据传输的共享内存，而其他的进程连接到这块共享内存，随后loop()等待event的通知读取共享内存中的数据执行对应的方法。

kv cache的显存创建

ModelRunner初始化时，会调用warmup_model()进行预热，构建 dummy tokens 进行模型的前向推理，同时记录 peak memory status。

全体进程根据peak memory status计算可用的显存容量创建kv_cache，当环境为单机多卡时，进程只需要创建切片后的 head 对应的显存。然后遍历持有的模型，逐层绑定对应的k_cache和v_cache。

Nano-vLLM 当前的实现并没有保证各进程之间显存容量对齐，各进程都是按照自己的可用显存计算 **num_kvcache_blocks 然后创建 cache 的块数，这种不一致性可能导致主进程对Block的调度出错。**

CUDA GRAPH的捕获和重放

当参数指示需要用CUDA GRAPH时，ModelRunner创建模型前向需要的占桩变量，随后执行模型的前向推理捕获对应的 CUDA 操作(这里会先warmup避免影响实际捕获的CUDA操作)。CUDA GRAPH 从bs大的开始捕获并创建graph pool, 最大可能复用显存减少无效的显存占用。捕获完成后，将占桩变量的引用记录到graph_vars , 之后重放时在对应位置写入数据即可实现参数的传递。当前的Nano-vLLM只在decode分支上重放CUDA GRAPH，因此 context中 prefill才需要的用到cu_seqlens_q/k max_seqlen_q/k 提供。所有 decode分支需要的变量的引用都保存在了graph_vars上。

2.5 LLMEngine

LLEngine 作为核心角色，串联起各个组件，从而实现推理。

单机多卡

当传入的tensor_parallel_size指示需要多卡时，主进程会创建多个子进程以ModelRunner作为进程的程序入口并传入一个Event，主进程会保存所有进程Event的引用来实现进程间的消息传递。主进程上创建一个Scheduler作为唯一的调度器，子进程只需要执行主进程的调度结果。
